## 🔍 Monitoring vs Observability

### Monitoring

Monitoring mainly helps us know **when something is wrong**.

For example:

-   CPU usage is above a threshold
-   Memory is too high
-   A server is down
-   An alert has been triggered

### Observability

Observability helps us investigate **why something is wrong**.

It allows us to explore metrics, logs and traces and correlate
information to understand the actual problem.

A simple way I understood it:

``` text
Monitoring     → What is wrong?
Observability  → Why is it wrong?
```

------------------------------------------------------------------------

# 🔭 Three Pillars of Observability

## 1. Metrics

Metrics are numerical values collected over time.

Examples:

-   CPU usage
-   Memory usage
-   Request count
-   Error rate

Tools:

-   Prometheus
-   Datadog
-   CloudWatch

For this project, I used **Prometheus**.

------------------------------------------------------------------------

## 2. Logs

Logs are timestamped records of events generated by applications and
systems.

Examples:

-   Application errors
-   Stack traces
-   Server events
-   Database errors

Tools:

-   Loki
-   ELK Stack
-   Fluentd

------------------------------------------------------------------------

## 3. Traces

Traces show the journey of a request across multiple services.

For example:

``` text
User Request
     ↓
API Service
     ↓
Payment Service
     ↓
Database
```

Tools:

-   OpenTelemetry
-   Jaeger
-   Zipkin

------------------------------------------------------------------------

## Why do we need all three?

I understood them like this:

``` text
Metrics → What is happening?
Logs    → Why did it happen?
Traces  → Where did it happen?
```

Example:

``` text
High error rate
      ↓
Metrics

Database timeout error
      ↓
Logs

Payment service took 12 seconds
      ↓
Traces
```

# 🏗️ Observability Architecture

The architecture I will build across the observability block is:

``` text
[Your App] --> metrics --> [Prometheus] --> [Grafana Dashboards]

[Your App] --> logs    --> [Promtail] --> [Loki] --> [Grafana]

[Your App] --> traces  --> [OTEL Collector] --> [Grafana/Debug]

[Host]     --> metrics --> [Node Exporter] --> [Prometheus]

[Docker]   --> metrics --> [cAdvisor] --> [Prometheus]
```

# ⚙️ Prometheus Configuration

I created `prometheus.yml`:

``` yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]

  - job_name: "notes-app"
    static_configs:
      - targets: ["notes-app:8000"]
```

### What this configuration does

Prometheus scrapes metrics every **15 seconds**.

I configured two scrape targets:

``` text
prometheus
notes-app
```

The Prometheus target points to:

``` text
localhost:9090
```

The Notes App target points to:

``` text
notes-app:8000
```

# 🐳 Docker Compose

I created `docker-compose.yml`:

``` yaml
services:
  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus
    command:
      - '--config.file=/etc/prometheus/prometheus.yml'
      - '--storage.tsdb.retention.time=30d'
      - '--storage.tsdb.retention.size=1GB'
    restart: unless-stopped

  notes-app:
    image: trainwithshubham/notes-app:latest
    container_name: notes-app
    ports:
      - "8000:8000"
    restart: unless-stopped

volumes:
  prometheus_data:
```

# 📚 Prometheus Metric Types

## Counter

A Counter normally only increases.

Examples:

``` text
Total HTTP requests
Total errors
Total processed jobs
```

Example:

``` text
http_requests_total
```

------------------------------------------------------------------------

## Gauge

A Gauge can increase or decrease.

Examples:

``` text
Current CPU usage
Current memory usage
Active connections
```

Simple difference:

``` text
Counter → goes up
Gauge   → goes up and down
```

------------------------------------------------------------------------

## Histogram

A Histogram is useful for measuring distributions.

For example:

``` text
Request duration
```

It can show how many requests fall into different duration buckets.

------------------------------------------------------------------------

## Summary

A Summary is also used for distributions and calculates
quantiles/percentiles on the client side.

# ⚠️ Notes App `/metrics` Finding

When Prometheus tried to scrape:

``` text
http://notes-app:8000/metrics
```

the target showed:

``` text
DOWN
```

with:

``` text
server returned HTTP status 404 Not Found
```

I verified this manually:

``` bash
curl -i http://localhost:8000/metrics
```

The result was:

``` text
HTTP/1.1 404 Not Found
```

I also tested from inside the Prometheus container:

``` bash
docker exec prometheus wget -S -O- http://notes-app:8000/metrics
```

and received:

``` text
HTTP/1.1 404 Not Found
```

So the problem was not Docker networking.

The Notes App is reachable on port `8000`, but this application does not
expose a Prometheus `/metrics` endpoint.

This was a useful troubleshooting lesson because a running application
does not automatically mean that Prometheus can scrape metrics from it.
